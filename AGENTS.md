# AGENTS.md — инструкции для AI-агентов в bbm-kb

Репо — база знаний холдинга BBM (мастер куррированных знаний + SSOT-ядро).
**Рабочий язык — русский** (контент, коммиты, комментарии).

## Правила SSOT — жёсткие

1. **`ssot/` = канон** (authority: canonical). Канонические факты — команда,
   миссия, сущности, сервисы, глоссарий, аббревиатуры — определяются только здесь.
2. **`content/` = нарратив** (authority: narrative). Нарратив **ссылается** на
   `ssot/`, не копирует и не переопределяет факты. Нужен факт на странице —
   ссылка на источник в `ssot/` или генерация на билде, не рукописная копия.
3. **Конфликт нарратива с каноном → канон перевешивает**, нарратив исправляется.
4. **Материалы встреч попадают в KB автоматически** — в
   `content/meetings/ГГГГ/ММ/`, по три представления на встречу: саммари и
   очищенная расшифровка страницами, исходник с таймингами файлом `.vtt` рядом.
   Их приносит сервис `bbm-academy-org/bbm-zoom-transcripts` (BBMP-220)
   пул-реквестом от имени `bbm-kb-meetings-bot`. Руками не правятся: изменения
   вносятся в источник или сервис и применяются при повторной обработке встречи.
   Служебные `meetings.json` и `meta.json` в папках месяцев тоже машинные.
   Аудиозаписи в KB не хранятся. Прочие рабочие драфты и исследования
   по-прежнему живут в репо `bbm`.
5. **Правки — только через PR.** Серверной branch protection нет (приватный
   репо на GitHub Free; включим при переходе орги на Team) — защита:
   конвенция «только PR», локальный pre-push hook (`.githooks/`,
   включение: `git config core.hooksPath .githooks`), CI-job `pr-guard`
   (краснеет на прямом пуше в main). Агент создаёт ветку, коммитит,
   открывает PR; прямой пуш в `main` запрещён правилом.
6. **Секреты** (ключи, токены) в репо и в PR не попадают.

## Параллельная работа — если задач несколько одновременно

Правила действуют, когда над репозиторием одновременно работают несколько
агентов (или агент и человек). Механика и обоснование — `docs/parallel-work.md`.

7. **Одна задача — один worktree.** Не работать в чужой рабочей копии и не
   переключать ветки в чужой. Свою получить командой
   `scripts/new-worktree.sh <slug>`: она отводит ветку от `origin/main`,
   выдаёт свободный порт дев-сервера в `.env.local` и ставит зависимости.
   Субагенты работают в директории своего оркестратора — им отдельная
   изоляция не нужна.
8. **Свой порт и только свой.** Порт выдан скриптом (слот N → `3000 + N×10`),
   лежит в `.env.local`, `next dev` берёт его сам. Соседние каталоги
   `bbm-kb-*` и их порты не трогать. Освобождать порт по завершении:
   дев-сервер, переживший сессию, выглядит для следующего агента как конфликт.
9. **`ssot/` — однопоточная зона.** Канон сводит все правки в одни файлы
   (правило 1), поэтому две задачи не правят `ssot/` одновременно. То же для
   `content/**/meta.json` одного раздела и для `package-lock.json`
   (там же PR-ы Renovate).
10. **Каталог `content/meetings/` руками не трогать** — машинная зона (правило 4),
    туда пишет `bbm-kb-meetings-bot`. Это не «осторожно», а «нельзя».
11. **Свою ветку держать короткой** и ребейзить на `origin/main` перед PR:
    `git fetch origin && git rebase origin/main && git push --force-with-lease`.
    Ветка живёт день-два. Большую задачу резать на несколько PR.
12. **Прежде чем кратно увеличивать объём данных** — проверить, кто эти данные
    читает: поиск (`app/api/search/route.ts`), оглавления, пропагация в Payload.
    Зелёный билд своей зоны ничего не говорит о соседях
    (`docs/parallel-work.md` §8).

## Master copy policy

Полная политика мастер-копий (v2) — в рабочем репо `bbm`:
`docs/master-copy-policy.md` (репо `sidorovanthon/bbm`). Суть:

- **Мастера знаний — здесь**: канонические факты в `ssot/`, куррированный
  нарратив в `content/`. Новые знания заводятся только в KB.
- **Notion — замороженный архив** (read-only, баннеры заморозки): ничего туда
  не писать, зеркалирование отменено.
- Рабочие драфты и исследования живут в репо `bbm`; созревшее знание переезжает
  сюда (мастер + стаб в старом месте, без копий).
  **Исключение — материалы встреч:** они попадают в KB напрямую и автоматически,
  минуя стадию «созревания» в `bbm` (см. правило 4).

## Механика

- Файл в `ssot/` = сущность с YAML-структурой/frontmatter (будущий ingestion
  в Knowledge Gateway). Схема записи описана комментарием в каждом файле.
- Перенос знания из `bbm`/Notion = переезд мастера сюда + стаб-указатель в
  старом месте. Никаких копий.
- Сайт: Fumadocs, статический экспорт (`npm run build` → `out/`). Страницы —
  `content/**/*.mdx`. Перед PR проверять, что `npm run build` зелёный.
- Скелеты `ssot/` и заглушки `content/` наполняются в задачах BBMP-99+;
  не наполнять контентом мимоходом, без задачи на курацию.
- Пропагация SSOT в потребители (Payload / cms.bbm.academy, Hermes-skill
  `hermes-skills/bbm-ssot/`) — `docs/ssot-propagation.md` (BBMP-102).
  Канонические поля публичного сайта руками не правятся — только через
  `ssot/facts/*` (иначе перезатрёт CI-джоб `propagate-payload`).
