# Параллельная работа: несколько агентов и людей в одном репо (BBMP-241)

Как вести две и более задачи одновременно — каждую своим агентом-оркестратором с деревом
субагентов — так, чтобы они не дрались за файлы, ветки и порты. Плюс что при этом меняется
для разработчика-человека.

Жёсткая выжимка правил — в `AGENTS.md`, раздел «Параллельная работа». Здесь — механика
и обоснование.

## Почему в bbm-kb это дёшево

У репозитория нет ни БД, ни Docker, ни `.env` с секретами: Fumadocs собирается в статику
(`output: 'export'`), состояние живёт в файлах. Поэтому весь общий ресурс — это:

| Ресурс | Общий? | Чем разделяется |
|---|---|---|
| Рабочая копия файлов | да | `git worktree` — своя директория на задачу |
| Ветка | да | своя ветка, создаётся вместе с worktree |
| Порт дев-сервера | да | слот: `3000 + N×10`, пишется в `.env.local` |
| `.next/`, `.source/`, `out/`, `node_modules/` | нет | лежат внутри worktree, в `.gitignore` |
| БД, Redis, Docker, `.env` | **их нет** | — |
| Деплой на kb.bbm.academy | да | сериализован в CI (`concurrency: kb-deploy`) |

**Это стоит защищать.** Каждый новый общий ресурс — БД, Docker, общий staging — делает
параллельную работу заметно дороже. Если задача требует такого, стоит сначала спросить,
можно ли обойтись без него.

## 1. Изоляция кода: git worktree

`git worktree` — вторая рабочая директория поверх того же `.git`: свои файлы на диске,
своя ветка, общая история и общий `origin`. Агенты не видят недоделанный код друг друга.

### Создание

```bash
scripts/new-worktree.sh bbmp-241-strategy-pages
```

Скрипт отводит ветку **от `origin/main`** (не от текущей — иначе в задачу утекут чужие
несмёрженные коммиты), занимает свободный слот, пишет `PORT` в `.env.local` и ставит
зависимости. В конце печатает готовый текст первого сообщения оркестратору.

Если репозиторий лежит в iCloud (как на рабочей машине Юлии), worktree лучше держать вне
синхронизируемой папки — иначе `node_modules` уедет в облако:

```bash
export KB_WORKTREE_ROOT="$HOME/bbm-kb-worktrees"
```

### Что наследуется, а что нет

**Наследуется автоматически:** `core.hooksPath` живёт в общем `.git/config`, поэтому
pre-push hook (запрет прямого пуша в `main`, правило AGENTS §5) работает в каждом worktree
без донастройки. Проверка: `git config core.hooksPath` внутри worktree → `.githooks`.

**Не наследуется:** `node_modules/` и `.source/` — их в свежем worktree нет. Нужен
`npm ci` (скрипт делает это сам). Кеш npm общий на машину, поэтому второй и последующие
прогоны быстрые.

### Гранулярность: worktree = задача = оркестратор

Субагенты одного оркестратора работают **в его рабочей директории** — разделять их между
собой не нужно и не получится, они делают части одной задачи. Изоляция нужна на уровне
«одна задача — один worktree — один оркестратор».

### Уборка после мёржа

```bash
git worktree remove ../bbm-kb-<slug>
git branch -d feat/<slug>
git worktree prune        # если каталог удалили мимо git
```

Не копить worktree: каждый занимает сотни мегабайт (`node_modules` Next.js) и путает —
легко открыть сессию в устаревшей копии.

## 2. Изоляция окружения: слоты, а не диспетчер

**Чего не делать:** заводить «оркестратора над оркестраторами», раздающего порты в
рантайме. Координация на лету хрупкая — она требует, чтобы обе стороны спрашивали
разрешения перед каждым действием, а они не спрашивают; плюс это лишний узел, способный
заблокировать обе задачи разом.

**Что делать:** окружение выдаётся один раз, при создании worktree, и выводится из номера
слота арифметически. Агент про соседей ничего не знает.

| Слот | Каталог | Порт |
|---|---|---|
| 0 | основной клон `bbm-kb` | 3000 |
| 1 | `bbm-kb-<slug>` | 3010 |
| 2 | `bbm-kb-<slug>` | 3020 |

Порт пишется в `.env.local` (файл в `.gitignore`), `next dev` подхватывает его сам —
флаги не нужны:

```bash
cd ../bbm-kb-<slug> && npm run dev
```

Скрипт выбирает свободный слот сам: читает `PORT` из `.env.local` всех существующих
worktree (не список слушающих сокетов — worktree с погашенным сервером всё равно держит
слот) и дополнительно проверяет порт через `lsof`.

## 3. Мёрж-конфликты: чего worktree НЕ решает

Worktree убирает конфликт «двое правят файл одновременно». Конфликт «две ветки изменили
один файл» он не убирает — переносит на мёрж, где он разбирается один раз и осознанно.

Поэтому **граница между параллельными задачами должна идти по архитектурному шву.** Две
задачи, заведомо лезущие в одни файлы, параллелить не надо вообще — изоляция не поможет.

### Файлы, которые конфликтуют чаще всего

| Файл | Почему | Что делать |
|---|---|---|
| `ssot/facts/*.yaml`, `ssot/abbreviations.yaml` | плоские реестры, все дописывают; правило SSOT «один факт — один дом» специально сводит всех в одно место | считать `ssot/` **однопоточной зоной**: одна задача на файл канона за раз |
| `content/**/meta.json` | оглавление и порядок страниц — общий список | не давать двум задачам добавлять страницы в один раздел; если неизбежно — заранее договориться о порядке мёржа |
| `package.json`, `package-lock.json` | меняются от любой установки зависимости; сюда же PR-ы Renovate | не ставить зависимости в двух задачах одновременно. При конфликте лока не мёржить руками: `git checkout origin/main -- package-lock.json && npm install` |
| `content/meetings/**` | машинная зона (AGENTS §4) | руками не трогать вообще, см. §4 ниже |

### Годные и негодные пары

- **Годно:** страницы `content/strategy/` + компонент поиска в `app/` — разные деревья.
- **Годно:** новый термин глоссария + правка CI — не пересекаются.
- **Негодно:** «добавить раздел» + «переструктурировать `content/`» — вторая трогает всё,
  что делает первая. Только последовательно.
- **Негодно:** две задачи, каждая дописывает в `team.yaml`.

## 4. Машинные участники: про них забывают

Кроме ваших агентов в репозиторий пишут ещё двое, и они не спрашивают разрешения.

**`bbm-kb-meetings-bot`** — сервис `bbm-academy-org/bbm-zoom-transcripts` (BBMP-220)
открывает PR с материалами встреч в `content/meetings/ГГГГ/ММ/`. По правилу AGENTS §4 эта
зона машинная: руками не правится, изменения вносятся в источник или сервис. Для
параллельной работы отсюда следует простое: **задачам туда нельзя**, а значит и конфликта
не будет. Но PR-ы бота мёржатся часто, поэтому долгоживущая ветка быстро отстаёт от `main`.

**Renovate** (`renovate.json`, `config:recommended`) открывает PR-ы на обновление
зависимостей — трогает `package.json` и `package-lock.json`. Если ваша задача ставит
зависимость, а Renovate в этот момент обновляет лок, конфликт лока гарантирован. Лечится
порядком мёржа (§5), не изоляцией.

## 5. Порядок мёржа

Правило репо — **только PR** (AGENTS §5). Оно же снимает координацию с агентов:
последовательность задаёт GitHub.

Первый PR мёржится, второй ребейзится на новый `main`:

```bash
git fetch origin
git rebase origin/main
git push --force-with-lease
```

`--force-with-lease`, а не `--force`: если в вашу ветку успел пушнуть кто-то ещё (агент,
человек, бот), пуш будет отклонён вместо тихой перезаписи чужой работы.

**Короткие ветки — главный рычаг против конфликтов**, важнее любой изоляции. Ветка живёт
день-два — конфликтов почти нет. Живёт неделю — конфликт гарантирован. Большую задачу
резать на несколько PR.

Гонки деплоя нет: job `deploy` помечен `concurrency: kb-deploy`, деплои идут по одному.
Два PR подряд дадут два деплоя, второй перетрёт первый — так и задумано, `rsync --delete`
зеркалит текущий `main`.

## 6. Осиротевшие дев-серверы

Самая частая «мистика» параллельной работы: агент поднял `npm run dev`, сессия
закончилась, процесс остался. Порт занят, следующий агент видит конфликт — хотя это мусор.

```bash
lsof -nP -iTCP -sTCP:LISTEN | grep -E 'node|next'   # что живо
kill "$(lsof -t -nP -iTCP:3010 -sTCP:LISTEN)"       # убить слот 1
```

Прогонять первую команду перед запуском параллели: двадцать секунд экономят полчаса
расследования.

## 7. Разработчик-человек

По коду не отличается от агента: своя ветка, свой PR, свой мёрж. По окружению у него всё
своё по определению — другая машина, другой localhost. Специального механизма не нужно.

Что требует внимания:

1. **`git config core.hooksPath .githooks`** — единственный шаг настройки, который легко
   забыть (README, раздел «Клонирование»). Без него можно случайно пушнуть в `main` мимо
   PR; CI это поймает (`pr-guard` покраснеет), но уже постфактум.
2. **Ревью становится узким местом.** Агенты производят PR быстрее, чем человек читает.
   По правилу репо ревью не обязательно, но если человека подключают именно ревьюером —
   считать его пропускную способность, иначе параллельность даст не ускорение, а очередь.
3. **Общих внешних ресурсов сейчас нет** — ни staging-БД, ни общих тестовых аккаунтов.
   Единственное общее — прод kb.bbm.academy, и туда пишет только CI. Если появятся, конфликт
   человека с агентами будет именно там, а не в портах.

## 8. Соседи, которые читают данные

Класс проблем, который изоляцией не лечится: изменение безупречно в своей зоне и ломает
того, кто эти данные потом читает.

Живой пример из этого репозитория: заливка архива встреч (91 страница, 326 тысяч строк)
прошла без ошибок — но поисковый индекс собирается на билде в один статический JSON,
который браузер качает целиком. Он вырос до 68 МБ и грузился 23 секунды, и всё это время
поиск не находил **ничего** — ни по новым встречам, ни по остальным разделам. Тесты были
зелёными и оставались верными: они проверяли не то место.

**Вопрос перед мёржем любой задачи, кратно увеличивающей объём данных:** кто ещё читает
эти данные и что у него станет с объёмом? Поиск (`app/api/search/route.ts`), боковое меню,
`meta.json` оглавлений, пропагация в Payload, sitemap.

Для параллельной работы это критично отдельно: две задачи, безобидные поодиночке, после
мёржа могут сложиться в проблему, которой не было ни в одной ветке.

## Чек-лист перед запуском параллели

- [ ] Задачи не пересекаются по файлам (таблица §3)
- [ ] Ни одна не трогает `ssot/` одновременно со второй
- [ ] Ни одна не лезет в `content/meetings/` (машинная зона)
- [ ] Осиротевшие дев-серверы убиты (§6)
- [ ] Каждой задаче создан worktree через `scripts/new-worktree.sh`
- [ ] Каждому оркестратору передан его каталог, ветка и порт (скрипт печатает текст)
- [ ] Обе ветки рассчитаны на день-два, не на неделю

## Чек-лист после

- [ ] Первый PR смёржен, второй отребейжен на новый `main`, CI зелёный
- [ ] Worktree удалены, ветки удалены
- [ ] Дев-серверы остановлены
- [ ] Проверено, не сложились ли задачи в проблему у «соседей» (§8)
